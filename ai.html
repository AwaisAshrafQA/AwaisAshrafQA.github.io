2Domain Skill

HOS Analyzer: From Production Issue to Reviewed Fix

The Problem
Reproducing a driver's Hours of Service (HOS) problem was the slowest part of fixing it. Recreating their data in a test environment took hours, often days, and edge cases had to be hit by trial again and again before anyone could start on a fix.
What I Built
A production HOS Analyzer made of a chain of internal Claude Code skills, each with one job. From a single request it gathers production signals about the driver's scenario (Datadog, Snowflake, the backend and Firebase), rebuilds the scenario and replicates it in the test environment, and creates permutations to explore the edge cases. It then runs each one against the code, traces the root cause, writes a fix and raises a pull request for developer review.
The Result
Reproducing a driver's scenario went from days to minutes. Issues are caught and understood sooner, QA can point to where the issue lies in the code rather than only report a symptom, and developers receive a fix PR to review instead of starting from scratch.

Deep Dive

How the HOS Analyzer Works

A chain of internal Claude Code skills, each with one job. From a single request it takes a driver's reported issue to a fix that a developer reviews.

Swipe sideways to see the full workflow →

AI skill Replay and iterate Root cause analysis Human review Outcome

Before

  • Recreating a driver's data in the test environment took hours, often days.
  • Critical issues, and ones that needed real data modelling, took the longest.
  • Edge cases had to be hit by trial, again and again, to reproduce the error.

After Minutes

  • One request pulls the production signals and rebuilds the scenario in test.
  • Permutations of the scenario are created on demand to explore edge cases.
  • The issue is traced in the code and a fix PR is raised for review.
  1. Gather SignalsCollects everything known about the scenario from Datadog, Snowflake, the backend and Firebase.
  2. Rebuild ScenarioTurns scattered signals into one picture: what the driver did, in what order, and the data around the error.
  3. Replicate in TestRecreates the scenario and driver data in a test environment, replacing days of manual data modelling.
  4. PermutationsCreates variations of the scenario to explore the edge cases around the original problem.
  5. Execute vs CodeRuns each scenario against the code and captures the response; results feed back into more permutations.
  6. Root CauseVerifies in the code where the issue lies and which edge cases trigger it.
  7. Write FixWrites the fix and handles the edge cases it found.
  8. Push Fix PRRaises a pull request. A developer reviews it and decides what ships.

Catch Issues Earlier

Ten QA Agents Built on Claude

A public Python project with an agent for each stage of QA work, from refining a user story to the release decision. Plain code computes the facts, such as boundary values, flip rates and quality gates. Claude adds the judgment, and guardrails in code have the final say. Run them from the command line and in CI through the Claude API, or ask Claude Code in plain English through ten matching Claude Code skills. Every agent applies a cited expert checklist: ISTQB v4.0.1, ISO 29148 and 25010, the OWASP API Security Top 10, RFC 9110 and published flaky-test and bug-report research.
